# Deep scan is opt-in

Since v0.3.0 the `scan` command collected one page after a fixed wait and reported it as "items found", with nothing to say it was the first render rather than a total: 20 reaction buttons of which 18 to 19 are liked, and 20 comment cards, against 133 liked cards in the same list once it was walked. The full walk is restored, but it is not the default. Plain `scan` keeps reading the first render, and `scan --deep` walks the Activity List to exhaustion.

The trade-off is between two kinds of wrong answer, and it cannot be had both ways at once. A default that reports the first render is quietly wrong: 20 cards presented as an item count under-reports a walked list more than twentyfold, and a user reading "19 items found" has no signal that a page was measured instead of a history. A default that walks is honest but slow for the smoke-test use the same command serves, and it would silently change what `scan` has meant since v0.3.0.

It qualifies as an ADR because it is hard to reverse: once the README, the changelog and the habit of a 19-item quick run all assume the shallow default, flipping it is a breaking change to scripts and expectations, not an edit. It is surprising without this context, because `--deep` reads like a convenience flag rather than the boundary between a page and a count. And it is the product of a real trade-off, measured rather than asserted: the probe reached 133 liked cards in 11 load steps and about 25 seconds, the shipped default then collected 410 liked cards in 111 steps and about four minutes on the same account, and a comments walk of comparable size is slower still and was not verified to completion (see `.scratch/deep-scan-scale/issue.md`). Cheap enough to offer, expensive enough and different enough in meaning to keep out of the default path, and the shallow default's 19 to 20 cards under-reports that history by more than twentyfold.
